---
name: operate
description: Use after a slice is built (to relate its concepts, plan sections, code and tests), when `mangsang impact` reports stale or broken relations, when `check` or `cq` fails, or when a project first adopts mangsang. Declares concepts (the net's nodes), proposes relations with evidence for a human to confirm, and disposes of staleness; never confirms on its own.
---

The engine is `mangsang.py` at this plugin's root: `python3 <plugin root>/mangsang.py <command> --target <project>` (`python` on hosts that have no `python3`).

1. First use — concepts before prose: `register` the plan document, the code modules and the test files, then declare the net's nodes *before* writing plan sections: `concept add NAME --means "one sentence" --by <name>` (or `--delegated`) for each idea the project is about. A plan section is a projection of a concept — write the section after the concept it projects, and relate it (`realizes`). Then declare the net's invariants (they answer to `check`): coverage of plan sections by code and by tests; `resolved`; `projection` — every concept realized in doc, code and test: `{"kind": "projection", "media": {"doc": ["plan/"], "code": ["src/"], "test": ["tests/"]}}`; and the reverse — every plan section belongs to a concept: `{"kind": "coverage", "predicate": "realizes", "anchors": "plan/PLAN.md#Q-*", "as": "src"}` (a section outside every concept is prose leading the net — red until a concept owns it or the person says why not). Then declare the domain questions (they answer to `cq`): what the *product* must answer — `cq add ID --text "the question" --verify '{"kind": "answered-by", "concepts": ["NAME"]}' --by <name>` — the named concept's `means` sentence is the answer; declaring the pairing is a judgment, so it is signed.
2. After a slice: propose relations in a `proposals.json` — `{"relations": [{"src", "predicate", "dst", "evidence"}]}` — the slice's section/symbols/tests each `realizes concept:NAME` (evidence quotes the concept's `means` or the projection's text), plus plan-section↔symbol (`documents`) and test↔symbol (`verifies`) where they say more than the concept does. The engine rejects proposals without evidence, with dead anchors, or outside the vocabulary. Show the list to the person; `confirm proposals.json --by <name>` on their word, or `--delegated "<why>"` (when the orchestrator declared the hand-off once with chongdae's `delegate`, pass that id — `--delegated D-xxxx` — and it is stored as a structured reference instead of a pasted reason). Then `observe --reset`.
3. Before editing a registered file: `lookup <path>` prints the confirmed relations standing on it and marks which ones the edit would make stale. Size the task as the edit *plus* those relation updates — one piece of work, not an edit now and an `impact` surprise later. (Guidance, not a gate: skipping it breaks nothing; `impact` still catches everything after.)
4. `impact` says stale: read the changed anchor against the section or test it is related to. If the sentence still holds, say so and `observe --reset`. If it does not, the section or test must change (that is work for a run), then reset. Never reset without reading.
5. `impact` says broken: the anchor was renamed or removed. If the *concept* is what moved (a section retitle, a symbol rename), the concept survives — `retire <id> --why` the broken projection and propose it again under the new anchor; the net's node needs no change. `concept rename` when the *name* itself changes; `concept revise --means` when the *meaning* changes (every projection goes stale — that is the net leading the documents, not following them).
6. `check` red is the net's health (a lint, not a question): FAILED (a declared invariant does not hold — propose the missing relations, step 2), UNASKABLE (the net moved out from under the invariant — its predicate or anchors are gone; `cq revise` it, with the person's word), UNWATCHED (the net holds something no invariant watches — declare one or tell the person why not).
7. `cq` red is the domain layer: FAILED (the answering concept is unrealized, or its projections moved since confirmation — re-read the concept against the code before trusting the sentence; then reconfirm or revise), UNANSWERABLE (the concept a question names is gone — the model cannot answer this of the domain; declare the concept or retire the question, with the person's word), UNQUESTIONED (a concept no question names — the model holds a meaning nobody asks for; write the question or say why not). Questions and invariants are declarations alike: `cq add/revise/retire` records who asked, refuses one the current model cannot support, and keeps retired ones in the record. Hand-editing cq.json records nothing — prefer the commands.

mangsang is optional for a project; when it is absent, whatever it would have watched is a non-claim, not a substitute.
