---
name: operate
description: Relate a slice's concepts, documents, code and tests; record conversations; answer stale or broken relations and failing check or cq. Sign your own judgments with reasons; a person's signature is only for what that person read, and delegation cites their recorded words.
---

The engine is `mangsang.py` at this plugin's root: `python3 <plugin root>/mangsang.py <command> --target <project>` (Python 3.11 or later).

1. First use — register the files that carry the contract, then declare concepts before prose: `concept add NAME --means "one sentence" --why "why this meaning holds"`. Check each boundary clause (every, only, never) against a projection, preferably a test exercising it; otherwise narrow the sentence or state the limit. A quote's presence does not prove its truth. Relate plan sections, symbols and tests to concepts. Declare the invariants the project needs: `registered` with folder prefixes, not just today's files; `coverage`; `resolved`; `projection` with media such as `{"doc": ["plan/"], "code": ["src/"], "test": ["tests/"]}`. Except with `{"glob": "...", "why": "..."}`; `*` crosses `/`, so prefer exact files unless every descendant is excluded. Declare domain questions with `cq add ID --text "..." --verify '{"kind":"answered-by","concepts":["NAME"]}' --why "why this question is asked"`.
2. After a slice: register its new files and relate its anchors in a proposals file (`{"relations": [{"src": "...", "predicate": "realizes", "dst": "concept:NAME", "evidence": "verbatim quote"}]}`). Add `documents` and `verifies` where they hold: a test must call the symbol and assert on what it does, not merely name it. Read both ends; `confirm proposals.json --why "what I read and why the link holds"` signs your own judgment. `--by NAME --approved-in source:ID` is only for what that person read; `--delegated source:ID --why "what judgment their words hand off"` is only for that recorded hand-off. Fix rejected proposals in the same file and confirm again. `observe --reset` is optional; it changes only the local observation baseline.
3. Before editing: `lookup PATH --brief` gives at most two lines — relations, concepts, stale/broken/disputed counts and the same-task re-read obligation, then any heading-rename warning. A registered file with no relation says impact cannot see its edits; an unregistered file covered by an invariant says check fails. Read full `lookup PATH` for the relations and quotes. Its closure includes same-file reads; across files, add relations. Size the task as the edit plus these re-reads. A task's own check is `impact --files <its files>` (exact paths; empty scope checks nothing); `--only` is a prefix.
4. Stale: read `impact --show` against both ends. Read a changed helper's own contract when `moved only through` or `shared` names it, and relate it or say whose detail it is. If the relation holds, `reconfirm ID --why "what was compared and why it still holds"`; the record keeps the diff (or why earlier text cannot be found), fingerprints and outcome. Never reconfirm unread. If it does not hold, change the projection and then re-read (`--evidence` for a new quote), or retire. A false meaning awaiting revision gets `concept drift NAME --why "what no longer holds"`, never reconfirmation. For many relations, `judge request --out DIR`, the judge worker, then `judge consume --response DIR/judge-response.json`; the judge signs, you apply. Never name a person as applier of verdicts they did not read.
5. Owed: read the concept against its remaining projections. `concept revise NAME --means "..." --why "why it changed"` if needed, otherwise `concept reaffirm NAME --why "what was compared and why the sentence still holds"`. The reaffirm keeps the sentence hash, current realizing anchors and lost projections. Reconfirming surviving relations does not answer the debt.
6. Broken: preview `move --dry-run`, then `move ID --why "what was compared and why it holds at its new home"` for an unambiguous same-key move or title-only heading rename. A moved relation whose text changed stays stale: re-read it. Otherwise retire and propose at the new anchor; the concept survives. `concept rename` changes its name, `concept revise` its meaning. Deleted files use `retire --gone FILE... --why "why removed"`; answer the owed concepts it names. Agents retire as themselves; unsigned retirement is allowed at a person's terminal.
7. `check` asks health: FAILED means an invariant does not hold; UNASKABLE means it cannot be asked; UNWATCHED means content no invariant watches. `unverified`/`untested` observe code without a proving test regardless of invariants. A projection's `test` medium needs `TEST verifies CODE` (or a non-test projection when there is no code); a test's `realizes` is navigation. Add only justified relations, or narrow an invariant with a reason. Answer unseen/unrelated files by registering and relating or excluding with a reason. `vocabulary --write` writes the engine's reading. Projects that require a model use `check --require-model` and a `required` invariant; a separate guard keeps only what the engine cannot express.
8. `cq` asks domain questions: FAILED means the answer's projections no longer support it; UNANSWERABLE means its concept is gone; UNQUESTIONED means a concept no question names. Re-read before revising, reaffirming or retiring with a reason. Prefer `cq add/revise/retire` to hand-editing records: declarations keep who judged them.
9. Conversations: ask the person's signing name (never derive it) and whether their words may be committed before the first source. Write `people.json` with `people` and actual host speaker prefixes (`"agents": ["Claude (", "Codex ("]`). Keep both sides verbatim with `source add`, an actual speaker and locator; short answers need `--replies-to`. `--from-transcript` supports Claude Code JSONL only (`~/.claude/projects/<the project path, / as ->/<CLAUDE_CODE_SESSION_ID>.jsonl`); for other transcripts use exact original words with `--file - --speaker WHO --locator WHERE`. Never reconstruct missing words. `--excerpt` keeps whole verbatim sentences when their context permits. Show meanings and questions: only a person's yes to that wording allows `--by NAME --approved-in source:ID`. Without it, declare as your own judgment with `--why` and put the meaning in the person's review queue; never use free-text `--delegated`. Relate your wording to your source and approval to theirs. Unanswered matters are open questions; show conflicting sources rather than settling them. A conversation-only model can use a `projection` invariant with `{"said": ["source:"]}`. `report --html NET.html` makes a derived local page; publish only when asked.
10. A person reviews a part at a time: `review queue` shows the packets; keep their response, then `review accept ID... --by NAME --approved-in source:ID` or `review reject ID... --by NAME --approved-in source:ID --why "their reason"`. Accept can name `concept:NAME`; a rejected meaning uses `concept drift`. `review status` shows progress; check never fails on review progress. `outcomes` measures what handled staleness led to. These review and outcome commands are Python CLI-only.

mangsang is optional; absent, what it would have watched is a non-claim. A passing lint is never a person's judgment.
